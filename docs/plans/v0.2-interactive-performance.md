# v0.2 - Interactive Performance

## Goal

Measure how a model behaves through `llama-server`, including startup time,
client-observed time to first token, end-to-end response time, prompt
processing, generation speed, and cache reuse.

This version reuses the configuration, execution, artifact, and reporting
foundations from `v0.1`.

The chronological implementation backlog is maintained in
[v0.2-todo.md](v0.2-todo.md).

## Phase 1 compatibility decisions

- Existing experiment files without a benchmark `track` remain valid and load
  as raw benchmarks.
- Raw results retain the `raw-v1` benchmark protocol. Interactive results use
  a separate `interactive-v1` protocol and are never compared as raw results.
- Result schema version 1 remains current because track identification is an
  additive field and old raw manifests and samples remain readable.
- Shared run metadata is separated from track-specific configuration and
  normalized measurements.

## User workflow

```powershell
llmbench server check --config configs/models/qwen-coder.yaml
llmbench interactive run --config configs/experiments/interactive.yaml
llmbench interactive report --latest
```

## Scope

### Server lifecycle

- Start `llama-server.exe` with an explicit model and runtime profile.
- Capture its command, logs, process ID, and startup timestamps.
- Poll the health endpoint until ready or timed out.
- Distinguish process startup from model-ready time.
- Terminate the complete server process tree during cleanup.
- Detect an occupied port and either fail clearly or use an allocated port.

### Request client

- Send streaming chat-completion requests.
- Use a monotonic high-resolution clock.
- Record request start, first content token, final token, and stream completion.
- Retain raw response events for debugging.
- Record server-reported timing and usage fields when available.
- Detect malformed streams, premature termination, and truncated output.

### Workload definitions

Create fixed interactive workloads for:

- Small input: approximately 500 tokens
- Medium input: approximately 4,000 tokens
- Large input: approximately 12,000 tokens

Use the server's tokenizer or token-counting capability to resolve actual input
tokens for the loaded model. Store both the target and actual token counts.

All measured requests in a comparable workload should use the same requested
output-token limit.

### Cold and warm measurements

Keep these separate:

- Server/model startup duration
- First request after model loading
- Warm uncached requests
- Warm cached-prefix requests

Warm-up requests must be marked and excluded from normal summary statistics.

### Statistics

Report:

- Median and p95 TTFT
- Median total response time
- Median prompt-processing tokens per second
- Median generation tokens per second
- Median completion-token count
- Cache-reuse tokens or ratio
- Error and truncation rates

## Out of scope

- Repository tools or agents
- Task correctness scoring
- A large prompt library
- Concurrent-user throughput testing
- Dashboard UI

## Acceptance criteria

- The runner reliably starts, detects readiness, and stops `llama-server`.
- A failed startup retains server logs and a structured failure reason.
- At least ten warm requests can be executed for each configured prompt size.
- TTFT is measured at the first streamed content token rather than the first
  HTTP byte.
- Warm-up, cold, warm, and cached runs cannot be mixed accidentally.
- Client timing and server timing are stored independently.
- Reports include median and p95 latency rather than averages alone.
- Automated tests cover stream parsing, timing aggregation, readiness timeout,
  and process cleanup behavior.

## Definition of done

`v0.2` is complete when the tool can answer how long a local model takes to
become ready and how responsive it feels for small, medium, and large prompts.
