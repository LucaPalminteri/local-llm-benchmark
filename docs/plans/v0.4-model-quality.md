# v0.4 - Model-Only Quality

## Goal

Add deterministic general-reasoning and one-shot coding evaluations where a
model receives a prompt, produces one answer, and cannot use repository tools
or retry after grading.

The purpose is to measure model capability independently from coding-agent
quality.

## User workflow

```powershell
llmbench tasks validate tasks/
llmbench quality run --suite configs/suites/quality-smoke.yaml
llmbench quality grade <run-id>
llmbench quality report <run-id>
```

## Scope

### Task format

Define a versioned task manifest containing:

- Stable task ID
- Track and category
- Prompt and system-prompt version
- Tags and difficulty metadata
- Sampling profile
- Output-token limit
- Timeout
- Grader type and configuration
- Public fixture paths

### General-reasoning tasks

Start with ten compact tasks covering:

- Logical reasoning
- Mathematical reasoning
- Instruction following
- Reading comprehension
- Long-context retrieval

Prefer deterministic answer formats that can be graded without subjective model
judgment.

### One-shot coding tasks

Start with fifteen tasks distributed across:

- TypeScript
- React
- Next.js
- Node.js
- Debugging and security review
- Test generation

Use executable graders where practical.

### Grader interface

Support graders such as:

- Exact or normalized answer
- Structured JSON answer
- Command-based tests
- TypeScript type checking
- Patch application followed by tests
- Explicit requirement checks

Run executable graders in isolated temporary working directories with timeouts.
The model response and grader output must be retained separately.

### Attempts and profiles

Support:

- Deterministic Pass@1 with a fixed seed and one attempt
- Recommended/native sampling with three attempts
- Consistency and best-of-three summaries

Keep thinking-token and output-token budgets explicit.

### Metrics

Report:

- Pass@1
- Mean score
- Consistency across attempts
- Best-of-three
- Truncation and invalid-output rates
- Generated tokens for correct and incorrect answers
- Correct answers per 100,000 generated tokens
- End-to-end time per successful task

## Security and validity

- Models cannot access graders, expected answers, or reference solutions.
- Graders cannot trust model-generated commands.
- Public and hidden task assets are clearly separated.
- Task changes create a new task version or protocol version.
- Grading does not depend on network access unless a task explicitly declares
  and controls it.

## Out of scope

- Repository exploration
- Tool calling
- Iterative debugging
- Agent retries
- Large public benchmark integrations
- Subjective style rankings as primary scores

## Acceptance criteria

- Task manifests are validated before a run starts.
- Ten reasoning and fifteen coding tasks run through one consistent interface.
- At least one exact-answer, structured-answer, and executable-test grader works.
- Hidden grader assets are absent from model-visible inputs.
- Pass@1 can be regenerated from stored responses and grader artifacts.
- Sampling, prompt, and output limits are stored for every attempt.
- Automated tests cover task validation, response parsing, grader isolation, and
  score aggregation.

## Definition of done

`v0.4` is complete when models can be compared on deterministic reasoning and
coding correctness independently from an agent framework.
