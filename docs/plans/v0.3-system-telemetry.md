# v0.3 - System Telemetry

## Goal

Correlate benchmark performance with resource consumption on the target Windows
11 and AMD Vulkan system.

The telemetry system must remain separate from experiment execution so new
measurement providers can be added without changing benchmark behavior.

## User workflow

```powershell
llmbench telemetry doctor
llmbench raw run --config configs/experiments/raw-full.yaml --telemetry
llmbench interactive run --config configs/experiments/interactive.yaml --telemetry
llmbench telemetry inspect <run-id>
```

## Scope

### Collector interface

Define pluggable collectors with a common lifecycle:

```text
prepare -> start -> sample repeatedly -> stop -> summarize
```

Each measurement must record:

- Timestamp
- Metric name and unit
- Value
- Measurement provider
- Process ID when attribution is possible
- Sampling interval

### Process measurements

Collect:

- Process working set
- Process private memory where available
- CPU utilization
- Process exit information

Include child processes when the experiment starts a process tree.

### GPU measurements

Research and implement a documented provider for the Windows 11 AMD Vulkan
setup capable of collecting:

- Dedicated GPU memory usage
- Shared GPU memory usage where available
- GPU utilization where available

Clearly distinguish total-device measurements from process-attributed
measurements. Never label total device usage as model-process usage.

### Sampling behavior

- Make the interval configurable.
- Use timestamps that can be aligned with benchmark events.
- Store raw time-series samples in JSONL.
- Calculate peak, median, and baseline-adjusted values.
- Record a short idle baseline before model loading when enabled.
- Exclude unsupported metrics using `null` plus an explanation.

### Environment capture

Expand `environment.json` with:

- Operating-system version
- CPU identity
- Installed and available RAM
- GPU identity
- GPU driver information when available
- `llama.cpp` build data
- Benchmark-tool version
- Relevant Git commit and dirty-worktree status

## Out of scope

- General system-monitoring UI
- Fan control or hardware tuning
- Automatic overclocking
- Cross-machine result normalization
- Energy measurement unless a reliable provider is available

## Acceptance criteria

- Telemetry can be enabled or disabled without changing experiment semantics.
- Raw telemetry samples align with server startup and request events.
- Peak process RAM is reported.
- Peak VRAM is reported with explicit measurement provenance.
- Unsupported counters produce a clear diagnostic rather than a false zero.
- Collector failure does not destroy otherwise valid benchmark results.
- Overhead is measured with a control run and documented.
- Automated tests cover sampling, timestamps, aggregation, missing metrics, and
  collector failure.

## Definition of done

`v0.3` is complete when performance reports can show speed and latency beside
trustworthy RAM and VRAM measurements with enough provenance to interpret them.
